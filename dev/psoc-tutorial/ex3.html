Exercise 3

LED Brightness via PWM

Generate a waveform in hardware and adjust it from C. The car's motor drive has the same structure.

On the car

This is the motor drive in miniature. On the car, a PWM component generates the switching waveform for the MOSFET board, and your control code adjusts one number — the compare value — to set torque. Practicing on an LED means your first PWM bug can't put a car into a wall.

Steps

Continue in the same project.

  1. Add the LED pin

    Place a Digital Output Pin, rename it LED, and assign it to P6[3] — that's LED4 on the board.

  2. Add the PWM component

    Place a PWM (Digital → Functions), name it PWM, and set PWM Mode = One output.

  3. Clock it and wire it

    Place a Clock component (System) configured for 10 kHz. Wire clock → PWM clock, and PWM pwm → the LED pin.

  4. Start it and control it from the ISR

    Add PWM_Start(); to the initialization section. Then make the button toggle brightness by editing the ISR from Exercise 2.

    Code check — your ISR after the edit 
    CY_ISR(inter)
{
    LCD_Position(0u, 0u);
    LCD_PrintString("Button Pressed");

    if (PWM_ReadCompare() == 0u) { PWM_WriteCompare(200u); }
    else                         { PWM_WriteCompare(0u);   }
}
  5. Build, program, press SW2

    The LED toggles between off and bright. Try other compare values (50, 100, 255) and watch the brightness follow.

What just happened

Core idea How PWM works: a counter and a comparison

Inside the PWM block, an 8-bit counter runs 0→255 over and over, advancing on each 10 kHz clock tick. The output is high while the count is below the compare value and low the rest of the period. Compare = 200 means high 200/255 ≈ 78% of the time — a 78% duty cycle.

The waveform is generated entirely in hardware. The CPU's only job is to poke the compare register occasionally; the pulses continue even if your code is busy or asleep. The car's speed control divides the work the same way: the PWM block makes the waveform, and the PID math in an ISR adjusts the compare value.

Going deeper Why it dims instead of blinking (signals view)

One full counter cycle takes 255 ticks at 10 kHz, so the LED switches at about 40 Hz — fully on, fully off, 40 times a second. Your eye can't follow that; it responds to the short-term average, so duty cycle reads as brightness.

In signals-and-systems terms, the square wave is a DC component (the average, proportional to duty cycle) plus harmonics at 40 Hz and up. Your visual system is a low-pass filter: it keeps the DC and rejects the harmonics. The car's motor does the same thing with its mechanical inertia — it can't accelerate at kilohertz rates, so it responds to the average voltage. PWM is how digital chips fake an analog output using only a switch, which is also why it drives motors so efficiently: a transistor fully on or fully off dissipates far less than one operated partway on.

Watch for it The LED sometimes "doesn't change" on a press

Mechanical switch contacts bounce: one press can produce several electrical edges within a few milliseconds, so the ISR runs twice and the brightness toggles twice; the net effect is nothing visible.

Here the consequence is cosmetic and the tutorial doesn't ask you to fix it. Remember the symptom, though: in Exercise 4 the same bounce silently corrupts timing data, and we fix it properly there.

Checkpoint

SW2 toggles LED4 between two brightness levels, the waveform runs in hardware, and you can explain why 40 Hz switching looks like dimming. The car's motor and servo drive will use this same pattern.
