Exercise 2

Button Push Interrupt

Make the chip react to a button press, and learn how the work divides between the schematic layer and the C layer.

On the car

Replace "button" with "Hall-effect sensor" and this is your speedometer: a magnet on the wheel passes the sensor, the pin sees an edge, an interrupt fires, your code counts it. The schematic and the code follow the same pattern in both cases.

Steps

This builds on your Exercise 1 project — keep the LCD.

  1. Add the button pin

    Place a Digital Input Pin (Ports and Pins), rename it Button, and set Drive mode = Resistive Pull Up in its configuration dialog. The button shorts the pin to ground when pressed, so the pull-up gives you 5 V idle, 0 V pressed.

  2. Add the interrupt component

    Place an Interrupt component (System), rename it Button_Interrupt, and set InterruptType = Rising Edge.

  3. Invert the signal

    A press produces a falling edge (5 V → 0 V), but the interrupt is looking for a rising one, so place a NOT gate (Digital → Logic → Not) between the pin and the interrupt. Wire the chain with the W key, clicking the start and end of each segment: Button → NOT → Button_Interrupt.

  4. Assign the pin — carefully

    Pins tab: Button = P6[1], which is push button SW2 on the board.

  5. Write the ISR and hook it up
    Code check — your whole main.c 
    #include "project.h"

CY_ISR(inter)
{
    LCD_Position(0u, 0u);
    LCD_PrintString("Button Pressed");
}

int main(void)
{
    CyGlobalIntEnable; /* Enable global interrupts. */

    LCD_Start();
    Button_Interrupt_Start();
    Button_Interrupt_SetVector(inter);

    LCD_Position(0u, 0u);
    LCD_PrintString("Hello World");

    for(;;)
    {
    }
}
  6. Build, program, press SW2

    "Hello World" should be replaced by "Button Pressed". Note that the main loop is empty; the ISR does all the work.

Gotcha: P6[1] is not P1[6]

The pin dropdown makes it easy to transpose the digits. P1[6] builds and programs without complaint, and the button does nothing. Check the small annotation next to the pin symbol in the schematic — it shows the actual assignment. This bug cost real time in the debugging session below.

Gotcha: the two lines everyone forgets

Button_Interrupt_SetVector(inter) — without it the interrupt fires into an empty default handler and your ISR never runs. And CyGlobalIntEnable; — without it every interrupt on the chip is masked. Both must be present.

What just happened

Core idea Why aren't the button and the LCD wired together?

Look at your schematic: the button chain and the LCD are separate islands, and that is correct. Schematic wires route hardware signals. The LCD is driven from C code through its API. The only "connection" between the button and the display is the body of your ISR.

This two-layer picture (a hardware layer drawn in the schematic, a code layer in C, meeting at component APIs and interrupts) is the central mental model for PSoC work. When something confuses you this semester, first ask which layer you are in.

Going deeper Interrupts vs. polling

You could detect the press without an interrupt by spinning in the main loop asking "is the pin low yet?" — that's polling. It burns CPU continuously, and if the loop is busy elsewhere it can miss short events.

An interrupt inverts control: dedicated hardware watches the pin, and when the edge arrives the CPU suspends whatever it was doing, runs your interrupt service routine (ISR), and resumes. This is the same mechanism your computer architecture course covers (vector table, context save, handler), at a scale small enough to see all the pieces. SetVector writes your function's address into the vector table.

On the car, interrupts are what let the PSoC time camera sync pulses and count wheel magnets while your control loop does math; nothing waits on anything else.

Going deeper The pull-up resistor, from your circuits course

The button connects the pin to ground and nothing else. Without a pull-up, an unpressed button leaves the pin floating — a high impedance node whose voltage wanders with coupled noise, reading as random logic levels.

"Resistive Pull Up" drive mode connects an internal resistor (~5.6 kΩ) from the pin to 5 V. Unpressed: no current flows, no drop across the resistor, pin reads 5 V. Pressed: the switch pulls the node to 0 V and roughly 1 mA flows through the resistor — small enough to waste no meaningful power, stiff enough to hold the node steady. It's a one-resistor application of the source / load reasoning from your circuits course, and it appears in most digital designs.

When it doesn't work — a real debugging session

Symptom, from building this walkthrough: pressing the button did nothing. Work this list in order; it's arranged from cheapest check to most thorough.

  1. Are you pressing the right button? The silkscreen must say SW2. One of the board's buttons is chip RESET, and pressing it reboots to "Hello World" — which looks like "nothing happens".
  2. Did you rebuild and reprogram after the schematic change? Schematic edits and pin assignments are baked into the programmed image; editing them does nothing until you program again.
  3. Diff your main.c against the listing above. ISR above main, both interrupt init lines present, names exactly matching the schematic component names.
  4. Check component configs: pull-up drive mode on the pin, Rising Edge on the interrupt, pin assigned to P6[1].
  5. Zoom in on wire endpoints. A wire that stops one grid square short of a terminal looks attached at normal zoom but isn't.
  6. Still stuck? Bypass the interrupt. Poll Button_Read() == 0u in the for(;;) loop and print. If polling works, the pin and hardware are fine and the problem is in the interrupt chain; if not, it's the pin config or assignment.

The actual bug that day was step 4: the pin was assigned P1[6] instead of P6[1] — diagnosed from a schematic screenshot, where the annotation next to the pin symbol read 1[6]. Fixed in Design Wide Resources → Pins, rebuild, reprogram.

Tip

Printing a shorter string over a longer one leaves stale tail characters on the LCD ("Button Pressedld"). Call LCD_ClearDisplay() before printing when messages vary in length.

Checkpoint

Pressing SW2 changes the display, via an ISR, with an empty main loop. You now know the hardware-layer/code-layer split, and you've debugged a silent failure with a systematic checklist.
