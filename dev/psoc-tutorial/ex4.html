Exercise 4

Timing Between Button Presses

Timer capture snapshots a running count the instant an event happens. This exercise also contains the hardest bug in the tutorial.

On the car

Speed sensing is this exercise verbatim: a magnet passes the Hall sensor instead of a thumb pressing SW3, the timer captures the count, and the time between captures gives wheel speed. Even the debounce fix at the end may reappear; the Hall sensor input can need the same treatment.

Steps

Continue in the same project. The plan: SW2 resets a free-running count (in hardware, via a wire), SW3 captures it and your code displays the elapsed time.

  1. Add the Timer

    Place a Timer (Digital → Functions), name it Timer. Configure: implementation UDB, resolution 16-bit, Period = Max (65535), Capture mode = Rising Edge, interrupt On Capture. (The tutorial recommends 32-bit timers for real projects; you'll see why below.)

  2. Clock it

    Fan out the existing 10 kHz clock: wire it to the timer's clock input as well as the PWM's. A clock can drive many blocks.

  3. Add the capture button

    New Digital Input Pin named Button2, Drive mode = Resistive Pull Up, assigned to P15[5] (push button SW3). Wire it to the timer's capture input.

  4. Wire the reset

    Branch the SW2 signal (after the NOT gate) to the timer's reset input. Make sure the branch point shows a junction dot — see the schematic checklist below.

  5. Add the capture interrupt

    New Interrupt component named Counter_Interrupt wired to the timer's interrupt output, with InterruptType = Rising Edge.

    Patch to the official tutorial

    The tutorial doesn't specify the interrupt type. Set Rising Edge explicitly: a "Level" interrupt without a status-register read in the ISR re-fires endlessly and the program appears to hang.

  6. Write the capture ISR

    Add #include <stdio.h> at the top of main.c for sprintf, start the timer in the init section (Timer_Start(); plus the Counter_Interrupt_Start() / _SetVector() pair), and add:

    CY_ISR(counter_inter)
{
    Timer_ReadStatusRegister();   /* clears sticky interrupt flags — do this FIRST */
    uint16 capture = Timer_ReadCapture();

    char strbuf[32];
    sprintf(strbuf, "ms: %u", (65535u - capture) / 10u);
    LCD_ClearDisplay();
    LCD_Position(0u, 0u);
    LCD_PrintString(strbuf);
}
    Patch to the official tutorial

    The tutorial's ISR omits Timer_ReadStatusRegister(). Reading it clears the timer's sticky interrupt flags; without it, the interrupt can wedge. Keep it as the first line.

  7. Keep both ISRs

    The Exercise 2/3 ISR (inter, on SW2) and this one (counter_inter, on SW3) coexist. Each Interrupt component gets its own CY_ISR function plus its own _Start() and _SetVector() calls. Don't delete the first ISR when adding the second.

    Code check — your whole main.c 
    #include "project.h"
#include <stdio.h>

CY_ISR(inter)
{
    LCD_Position(0u, 0u);
    LCD_PrintString("Button Pressed");

    if (PWM_ReadCompare() == 0u) { PWM_WriteCompare(200u); }
    else                         { PWM_WriteCompare(0u);   }
}

CY_ISR(counter_inter)
{
    Timer_ReadStatusRegister();
    uint16 capture = Timer_ReadCapture();

    char strbuf[32];
    sprintf(strbuf, "ms: %u", (65535u - capture) / 10u);
    LCD_ClearDisplay();
    LCD_Position(0u, 0u);
    LCD_PrintString(strbuf);
}

int main(void)
{
    CyGlobalIntEnable;

    LCD_Start();
    PWM_Start();
    Timer_Start();

    Button_Interrupt_Start();
    Button_Interrupt_SetVector(inter);
    Counter_Interrupt_Start();
    Counter_Interrupt_SetVector(counter_inter);

    LCD_Position(0u, 0u);
    LCD_PrintString("Hello World");

    for(;;)
    {
    }
}
  8. Build, program, test

    Press SW2 (reset), wait a few seconds, press SW3, and the elapsed time appears. Vary the pause and check the number follows it.

Three facts the tutorial leaves out

All three came up in practice while building this walkthrough.

Fact 1 The UDB timer counts down

It starts at the period (65535) and decrements, so a longer pause gives a smaller capture value. Elapsed ticks = 65535 − capture, and at 10 kHz, milliseconds = (65535 − capture) / 10 — that's why the ISR above does that arithmetic. The tutorial's own screenshot shows raw down-counts without comment, which is confusing if you expect counts to go up.

Fact 2 16 bits at 10 kHz wraps every 6.55 seconds

A 16-bit counter has 65536 states; at 10,000 ticks per second it exhausts them in about 6.55 s and wraps around. Pause longer than that and the displayed time is the true time modulo 6.55 s: a wrong answer that looks fine.

This is the same modular arithmetic behind integer overflow in your programming courses, and it's why the tutorial recommends 32-bit timers for real projects: 232 ticks at 10 kHz is almost five days. Try a 10-second pause to see it happen.

Fact 3 Capture fires when you release SW3

The pin idles high (pull-up), goes low while pressed, and rises on release. Capture is set to rising edge, so the snapshot happens at release. For casual testing the difference is small; for precise measurements it matters which edge you're timing.

The bug: every interval read ~1000 ms

Real symptom from building this walkthrough: no matter how long the pause between SW2 and SW3, the display showed roughly 1000 ms. It is worth retracing because each step is a technique you will reuse.

  1. Question the measurement before the instrument. First hypothesis: the "pause" being varied wasn't the gap being measured. People press SW2-then-SW3 with a very consistent rhythm (~1 s) and vary the pause between trials. Controlled test: fast / 3-mississippi / 5-mississippi trials, expecting ordering and rough proportionality (~300 / ~3000 / ~5000 ms). The readings stayed ~1000 ms — hypothesis rejected, and now the symptom is precise.
  2. Sweep the configs. This turned up two real (if secondary) issues: Button2 had to be set to Resistive Pull Up — a floating input generates spurious capture edges, and Counter_Interrupt was confirmed Rising Edge, with Timer_ReadStatusRegister() added to the ISR.
  3. Photo-review the schematic against a checklist:
    • Junction dots where branches start (the reset branch off the NOT-gate output needs one).
    • Wires crossing without dots are correct non-connections — a dot there would short two nets, and the build fails with a multiple-driver error.
    • Pin annotations readable next to each pin symbol — this check is what caught the P1[6]/P6[1] transposition back in Exercise 2.
  4. The actual culprit: switch bounce + capture FIFO staleness. The UDB timer's capture register is a small FIFO. A bouncy SW3 release queues several captures within milliseconds, and Timer_ReadCapture() returns the oldest entry, so every trial displayed a leftover value from a previous press cluster. The ~1000 ms was the rhythm of the previous trial rather than the current pause.
  5. The fix: a Debouncer component on Button2, clocked by a new 100 Hz clock (Clock_Slow). Wiring: Button2 → Debouncer d, Debouncer q → Timer capture, Clock_Slow → Debouncer clock. Debouncing SW2 too is optional and wasn't needed.
    Why a new 100 Hz clock

    Do not reuse the 10 kHz clock. The Debouncer requires the input stable for a couple of its clock periods: at 10 kHz that's ~0.2 ms, and bounce sails through. At 100 Hz it demands ~20 ms of stability, which real bounce cannot produce.

Going deeper What bounce is, physically

A button is two pieces of springy metal. On contact they literally bounce — striking, separating, and re-striking for a few milliseconds before settling. The pin voltage during that window is a burst of edges, and hardware fast enough to see microseconds (interrupts, timer captures) sees every one of them as a distinct event.

In Exercise 3 bounce was cosmetic (a double-toggled LED); here it corrupted data. The Debouncer, a small state machine that requires the input to hold steady for ~20 ms before accepting the change, fixes it in hardware. Treat any mechanical or noisy edge on the car with the same suspicion.

Checkpoint

The displayed interval tracks your actual pause across fast / 3-second / 5-second trials, resets on SW2, and survives repeated presses without going stale. You've used hardware capture, converted down-counts to milliseconds, seen 16-bit rollover, and debounced a real input.
